TCP 연결은 세 번의 교환으로 열리고 네 번의 교환으로 닫힌다. 닫은 쪽은 바로 사라지지 않고 60초쯤 남아 있는데, 이 잔류가 서버에서는 실제 문제가 된다.

![3-way와 4-way 핸드셰이크](attachments/handshake.svg)

## 1. 플래그와 시퀀스 번호

### 1.1 주요 플래그

| 플래그 | 의미 |
|---|---|
| SYN | 연결 요청, 시퀀스 번호 동기화 |
| ACK | 수신 확인 |
| FIN | 종료 요청 |
| RST | 강제 종료 |

### 1.2 시퀀스 번호 규칙

핸드셰이크를 이해하려면 번호가 어떻게 움직이는지 먼저 알아야 한다.

- **시작값(ISN)은 랜덤이다.** 0부터 시작하지 않는다
- **seq 증가량은 보낸 바이트 수다.** 세그먼트 개수가 아니다
- **ack 값은 "상대 seq + 상대가 보낸 바이트 수"** — 다음에 기대하는 번호를 뜻한다
- **SYN과 FIN은 데이터가 0바이트여도 번호를 1 소비한다.** 팬텀 바이트라 부른다

마지막 규칙 때문에 핸드셰이크에서 `+1`이 계속 등장한다.

## 2. 3-way 핸드셰이크 — 연결 수립

세그먼트 3개를 교환한다.

### 2.1 1단계: SYN (Client → Server)

- **SYN** = Synchronize. 시퀀스 번호를 맞추자는 요청
- **ISN** = Initial Sequence Number. 이 연결에서 클라이언트가 쓸 시작 번호

### 2.2 2단계: SYN + ACK (Server → Client)

- 서버도 자기 ISN을 보내며 동기화를 요청한다
- `ack = X + 1` — X번까지 받았고 다음은 X+1을 기대한다는 뜻

### 2.3 3단계: ACK (Client → Server)

클라이언트가 서버의 SYN에 대해 수신을 확인한다.

### 2.4 상태 전이

```
1단계 후: Client SYN_SENT / Server LISTEN → SYN_RECEIVED
3단계 후: 양측 ESTABLISHED
```

## 3. 4-way 핸드셰이크 — 연결 종료

닫을 때 한 번이 더 필요한 이유는, TCP가 **양방향을 각각 닫기** 때문이다.

### 3.1 1단계: FIN (Active Close → Passive Close)

- `seq = u`
- 상태: ESTABLISHED → **FIN_WAIT_1** / 상대는 CLOSE_WAIT

### 3.2 2단계: ACK

- `ack = u + 1`
- 상태: FIN_WAIT_1 → **FIN_WAIT_2**
- **Half-Close** — 이 시점에 상대는 남은 데이터를 계속 보낼 수 있다. 이게 4단계인 이유다

### 3.3 3단계: FIN (Passive Close → Active Close)

- `seq = v`
- 상대 상태: LAST_ACK

### 3.4 4단계: ACK

- `ack = v + 1`
- 상태: **TIME_WAIT**(2MSL 대기) → CLOSED / 상대는 즉시 CLOSED

## 4. TIME_WAIT

### 4.1 왜 즉시 닫지 않나

먼저 연결을 끊는 쪽은 **자신의 마지막 ACK가 상대에게 도달했는지 확인할 방법이 없다.** 그 ACK에 대한 응답은 오지 않기 때문이다.

그래서 즉시 종료하지 않고 2MSL(보통 60초) 동안 4-tuple을 점유한 채 남는다. 목적은 두 가지다.

- **마지막 ACK가 유실된 경우 대비.** 상대가 FIN을 재전송하면 응답해 줄 주체가 필요하다
- **떠도는 이전 세그먼트가 새 연결을 오염시키지 못하게 차단.** 같은 4-tuple로 새 연결이 열렸을 때, 늦게 도착한 옛 패킷이 섞이면 안 된다

### 4.2 시퀀스 번호와의 관계

ISN이 랜덤인 것도 여기에 걸린다. 늦게 도착한 패킷이 새 연결의 시퀀스 번호 범위에 들어오지 않아야 유효성 판단으로 걸러낼 수 있다.

### 4.3 서버에서 문제가 되는 지점

TIME_WAIT은 **먼저 닫는 쪽**이 감당한다. 보통은 클라이언트지만, 서버가 먼저 닫는 구조라면 서버가 전부 떠안는다.

소켓 하나당 커널 구조체를 차지하므로, 초당 요청이 많으면 커널 테이블을 압박한다. 초당 1000개 요청이면 60초 동안 6만 개가 상시 잔류한다.

HTTP/1.0이 요청마다 연결을 닫았다가 1.1에서 지속 연결로 뒤집힌 이유 중 하나가 이것이다.

## 5. 정리

- 열 때 3번, 닫을 때 4번인 이유는 **닫기가 양방향 각각 진행**되기 때문이다
- TIME_WAIT은 낭비가 아니라 **마지막 ACK를 책임지기 위한 대기**다
- 그 비용은 먼저 닫는 쪽이 낸다
