>[!IMPORTANT]
>웹에서 CCTV 영상을 내보내는데 1~2초씩 밀렸다. 원인을 따라가 보니 TCP가 제공하는 신뢰성이 실시간 영상에서는 오히려 손해라는 결론에 닿았다.

## 1. 신뢰성 4요소
TCP가 제공하고 UDP가 제공하지 않는 것은 네 가지다.

| 요소       | TCP | UDP |
| -------- | --- | --- |
| 순서 보장    | O   | X   |
| 오류 검출    | O   | 부분적 |
| 재전송      | O   | X   |
| 흐름·혼잡 제어 | O   | X   |

오류 검출만 애매한데, UDP도 체크섬은 가지고 있다. 다만 **틀렸다는 것만 알고 복구는 하지 않는다.** 깨진 패킷을 버릴 뿐이다.

## 2. 자주 이어지는 질문 3개

### 2.1 UDP는 왜 존재하나

4요소가 항상 이득이 아니기 때문이다.

실시간 통신에서는 재전송이 오히려 해롭다. 늦게 도착한 데이터는 가치가 없다. 이미 지나간 0.5초 전 화면을 다시 받아봐야 쓸 데가 없고, 그걸 기다리느라 지금 화면이 멈춘다.

### 2.2 그럼 UDP로 신뢰성이 필요하면

앱이 페이로드 앞에 자체 헤더를 붙여 직접 구현한다. RTP와 QUIC이 실제로 그렇게 한다.

### 2.3 UDP 위에 다 만들 거면 TCP를 쓰지 왜

두 가지 이유가 있다.

- **필요한 것만 골라 쓸 수 있다.** 순서 보장은 필요한데 재전송은 싫다면, TCP로는 그렇게 못 한다.
- **TCP는 커널에 박혀 있어 개선이 어렵다.** UDP 위에 만든 것은 앱 업데이트만으로 배포된다. HTTP/3가 QUIC 위에 올라간 이유이기도 하다.

## 3. 실제로 겪은 문제

### 3.1 상황

웹 환경에서 RTSP 카메라 영상을 제공해야 했다. HLS 방식으로 구현했더니 1~2초 지연이 발생했다.

### 3.2 원인 — HLS는 TCP 위에 있다

HLS는 HTTP 기반이고, HTTP는 TCP 위에서 돈다. 지연은 두 층에서 각각 발생한다.

**HLS 자체의 지연**

- 세그먼트 생성 대기 — 영상을 일정 길이 단위로 잘라 파일로 만든 뒤에야 내보낼 수 있다
- 버퍼링
- HTTP 폴링 오버헤드

**TCP의 지연**

패킷이 유실되면 재전송이 완료될 때까지 **뒤에 도착한 모든 데이터가 대기한다.** 이미 도착해서 바로 보여줄 수 있는 화면도 순서 때문에 못 나간다. 결과는 화면 정지다.

앞서 말한 "재전송이 오히려 해롭다"가 그대로 나타난 것이다.

### 3.3 해결 — WebRTC

UDP 위에서 동작하는 WebRTC로 바꿨다. WebRTC는 단일 프로토콜이 아니라 묶음에 가깝다.

- RTP/SRTP — 미디어 전송
- DTLS — 암호화, 필수
- ICE/STUN/TURN — NAT 통과
- SCTP — 데이터 채널
- SDP — 협상 형식

여러 요소가 지연을 줄이는 데 기여하지만, **압도적인 이유는 세그먼트가 없는 구조**라는 점이다. 파일로 잘라 만드는 단계가 사라지면 그 대기 시간이 통째로 없어진다.

## 4. 정리

TCP의 신뢰성 4요소는 기능이지 미덕이 아니다. 데이터가 늦더라도 정확해야 하는 곳에서는 이득이고, 늦으면 가치가 사라지는 곳에서는 비용이다.

실시간 영상은 후자였다. 그래서 UDP로 내려가서 필요한 것만 골라 다시 쌓았다.
