HTTP 메서드가 왜 GET, POST 같은 정해진 몇 개뿐인지 생각해 본 적이 있다. 헤더에 `X-My-Intent: fetch-user`라고 써도 될 것 같은데 그렇게 하지 않는다. 이유를 따라가다 보니 stateless와 멱등성까지 이어졌다.

## 1. Stateless

### 1.1 상태가 없다는 뜻이 아니다

**stateless ≠ 상태가 없다.** 요청 사이의 **세션 상태**를 서버가 유지하지 않는다는 뜻이다. 더 정확히는 **상태가 특정 서버 프로세스의 메모리에 묶여 있지 않다**는 것이다.

| 구분        | 예시                  | stateless와의 관계      |
| --------- | ------------------- | ------------------- |
| 애플리케이션 상태 | DB의 사용자·주문          | 무관. 당연히 있다          |
| 세션 상태     | "이 클라이언트는 3단계 진행 중" | 이걸 프로세스 메모리에 안 두는 것 |

반대로 **stateful**은 이전 맥락을 프로세스 메모리에 잡아두는 것이다. 결과적으로 같은 서버로 요청이 가야 한다(sticky). 다만 sticky는 정의가 아니라 **결과**다. 정의는 "묶여 있다"는 쪽이다.

### 1.2 이점 — 불가능한 게 아니라 비싸지는 것

흔히 stateless의 이점으로 꼽는 것들은, stateful에서 불가능한 게 아니라 대가를 치르고 가능해진다.

| 이점 | stateful에서 | 대가 |
|---|---|---|
| 수평 확장 | sticky session으로 가능 | 부하 불균형, 오토스케일 반쪽, 배포가 세션 길이에 묶임 |
| 장애 격리 | 세션 복제로 가능 | 복제 트래픽 O(N), 일관성 문제 |
| 중간 노드 자유 | 매핑 테이블로 가능 | 그 테이블이 상태 → LB가 새 SPOF |

### 1.3 가장 결정적인 차이는 장애 회복 방식

```
stateless: 요청 실패 → 다른 서버에 재전송 → 끝  (재시도)
stateful : 연결 끊김 → 세션 소멸 → 처음부터    (재협상)
```

RTSP가 좋은 예다. `SETUP`으로 Session ID를 받고 `PLAY` 중에 서버가 죽으면, `PLAY`를 재전송해도 실패한다. 그 ID를 아는 서버가 없기 때문이다. `DESCRIBE`부터 다시 해야 한다.

**`PLAY`는 멱등해 보이지만 서버 측 상태에 의존해서 재시도가 성립하지 않는다.**

### 1.4 상태를 없앤 게 아니라 옮긴 것

```
프로세스 메모리 → 클라이언트(JWT) 또는 외부 저장소(Redis)
```

| | 프로세스 메모리 | JWT | Redis |
|---|---|---|---|
| 서버가 죽으면 | 소멸 | 살아있음 | 살아있음 |
| 대가 | 없음(가장 빠름) | 즉시 폐기 불가, 매 요청 전송 오버헤드 | 추가 홉, Redis가 새 SPOF |

**"서버는 stateless, 시스템은 stateful."**

참고로 JWT의 전송 오버헤드는 HTTP/2의 HPACK과 HTTP/3의 QPACK이 존재하는 이유이기도 하다. stateless의 비용을 전송 계층에서 되돌리는 패치인 셈이다.

### 1.5 어느 쪽을 고를까

상태를 매 요청에 실어 보내는 비용과 프로세스에 묶는 대가 사이의 트레이드오프다. 상태가 적으면 stateless, 초당 수십 번 갱신되는 종류라면 stateful이 맞다.

## 2. HTTP 메서드

### 2.1 왜 필요한가 — stateless의 결과물

의도를 저장해 둘 곳이 없으므로 매 요청이 스스로 선언해야 한다. 메서드가 그 **의도 선언**이다.

stateful이었다면 연결 시작 시 한 번 협상하면 됐다. FTP와 텔넷이 실제로 그렇게 한다.

### 2.2 왜 "미리" 보내는가 — 파싱 편의가 아니다

**본문이 아직 도착하지 않았기 때문이다.** TCP는 스트림이라 헤더와 본문이 시간적으로 분리돼 도착한다.

| 판단 | 본문이 필요한가 |
|---|---|
| 메서드 미지원 `405` | X |
| 인증 `401` | X |
| 크기 초과 `413` | X |
| 백엔드 라우팅 | X |

의도가 본문에 있었다면 **거부할 요청의 5MB를 전부 받은 뒤에야 거부**할 수 있다. DoS 벡터가 된다. `Expect: 100-continue`가 성립하는 이유가 이것이고, chunked라면 본문은 끝나지 않을 수도 있다.

### 2.3 왜 "고정 어휘"여야 하는가

여기가 핵심이다.

`X-My-Intent: fetch-user-cacheable`도 헤더에 있으니 시간 문제는 해결된다. 그런데 **CDN이 못 읽는다.** 읽게 만들려면 서비스 규칙을 알려줘야 하고, 그러면 서비스별 설정이 생기고, 결합이 발생한다. 범용 프록시가 불가능해진다.

> **메서드가 고정 어휘인 이유 = 애플리케이션이 무슨 서비스인지 몰라도 요청의 의미를 알 수 있게 하는 것.**

이게 CDN·프록시·브라우저 캐시라는 인프라가 존재할 수 있는 조건이다. 그래서 다음 판단들이 가능해진다. 전부 위 원칙의 **결과**다.

- 캐시 서버: safe(GET) → 응답 저장 가능
- 프록시/LB: idempotent → 타임아웃 시 다른 서버로 재시도
- 브라우저: POST → 뒤로가기 재전송 경고, prefetch 여부 판단
- LB: GET → read replica / 쓰기 → primary
- 관측성: 본문 파싱 없이 엔드포인트별 지표 수집

### 2.4 반증 사례 — GraphQL

GraphQL은 전부 `POST /graphql`이고 의도는 본문에 있다. 그래서 잃는 것이 명확하다. HTTP 캐시, 프록시 재시도, 엔드포인트별 관측성, 경로 기반 레이트리밋.

우회책은 전부 **애플리케이션을 아는 전용 인프라를 새로 만드는 것**이다. 파싱 속도가 문제였다면 파서만 빠르게 하면 됐다. 실제로 잃은 건 **범용 인프라 호환성**이다.

### 2.5 대가

고정 어휘는 표현력이 부족하다. PATCH가 나중에 별도 RFC로 추가됐고, WebDAV는 `PROPFIND`·`MKCOL`을 새로 만들었다. 실무에서 `POST /orders/1/cancel` 같은 RPC 스타일이 흔한 것도 같은 이유다.

**표현력을 버리고 범용성을 산 거래다.**

## 3. 멱등성

### 3.1 정의

**같은 요청을 N번 보내도 서버의 최종 상태가 1번 보낸 것과 같은 성질.**

응답은 달라도 된다. `DELETE`는 첫 번째에 204, 두 번째에 404를 반환할 수 있다. **서버 상태에 대한 계약이지 응답에 대한 계약이 아니다.**

### 3.2 왜 필요한가 — TCP가 못 푸는 문제

```
POST → 서버 처리 완료 → 응답 유실
클라이언트: (a) 요청이 안 갔나?  (b) 처리됐는데 응답만 유실인가?  → 구별 불가
```

TCP는 바이트의 도달을 보장하지만 "서버가 이미 처리했는가"는 알려주지 않는다.

**멱등성 = 애플리케이션 계층의 재시도 안전성 판정 속성.** TCP가 세그먼트 단위로 푼 문제를 HTTP가 요청 단위로 다시 푼 것이다.

### 3.3 HTTP의 역할 범위

HTTP는 멱등성을 **보장하거나 실행하는 주체가 아니다.** "반복해도 같은 효과여야 한다"는 **의미 규약**만 부여한다.

실제 보장은 **서버의 데이터 처리 로직과 저장 방식**이 한다.

### 3.4 세 성질은 직교한다

| 성질 | 의미 |
|---|---|
| Safe | 서버 상태를 변경할 의도가 없음 |
| Idempotent | 반복해도 최종 상태 동일 |
| Cacheable | 응답 재사용 가능 |

`Safe ⊂ Idempotent`로 한 방향만 성립한다. DELETE는 unsafe하지만 멱등이다.

- **멱등**: GET, HEAD, OPTIONS, TRACE, PUT, DELETE
- **비멱등**: POST, PATCH

### 3.5 PUT vs POST vs PATCH — 근원은 하나

- **PUT** = 선언형. "이 URI 상태를 이걸로 만들어라" → 절대 상태 지정 → 멱등
- **POST** = 명령형. "이 데이터를 처리해라" → 호출마다 새 리소스 → 비멱등
- **PATCH** = 둘 다 표현 가능 → 스펙이 보장하지 못함

```json
[{"op":"add","path":"/tags/-","value":"x"}]   // 상대 연산 → 비멱등
{"name":"Dean"}                                // 절대값  → 결과적으로 멱등
```

> **멱등성은 메서드 이름이 아니라 연산이 절대값이냐 상대값이냐에서 나온다.**

### 3.6 POST를 재시도 가능하게 — Idempotency-Key

```http
POST /payments
Idempotency-Key: 550e8400-...
```

서버 동작은 이렇다.

- 처음 본 키 → 처리한 뒤 (키 → 응답)을 저장
- 이미 본 키 → **재처리 없이 저장된 응답을 반환**

**프로토콜에서 멱등성을 얻지 못하면 상태 저장으로 만들어낸다.** TCP 시퀀스 번호가 중복 세그먼트를 걸러내는 것과 같은 아이디어다. Stripe와 Toss가 쓰는 표준 패턴이다.

## 4. 한 줄씩 정리

- **메서드는 "빨리 읽으려고" 있는 게 아니라 "모르는 사람도 읽을 수 있게" 하려고 있다**
- **멱등성은 응답에 대한 약속이 아니라 서버 최종 상태에 대한 약속이다**
- **stateless는 상태를 없애는 게 아니라, 상태를 특정 프로세스에서 떼어내 아무나 대신할 수 있게 만드는 것이다**
